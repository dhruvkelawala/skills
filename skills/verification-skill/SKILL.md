# Verification skill

An agent that built a feature should be able to prove it works by running the app itself, without a human. This skill writes the project-local skill that makes that possible, and keeps it in step with the app.

Invoke as `/verification-skill create [app]` or `/verification-skill check [verify-<app>]`. A bare `/verification-skill` runs `check` when the repo has `.agents/skills/verify-*/` and `create` when it does not.

`EVIDENCE.md` owns the per-change proof checklist and where captures are published, and the verify skill links to it. `/verify` runs the repository's checks, not the live app.

## What a verify skill contains

`.agents/skills/verify-<app>/SKILL.md` has `name: verify-<app>`, a description that names the app, its surface and when to use it, and these sections, each built from commands that ran:

- **Hazards.** These five, each with the step or guard that keeps it in this app:
  - Kill only what this run started.
  - Never drive production. Name the environments a run may drive, and guard the rest so the guard fails closed: a run that can't tell where it points stops.
  - Never touch the user's own install or data. When a run needs the user's own device, back their data up first.
  - Never print env values, tokens or URLs that carry credentials. Print a variable's name and whether it is set.
  - Bind servers to loopback, and have doctor prove it.
- **Isolation.** The inventory, a table of every resource a run touches that another run or the user could also hold: ports, including ones compiled into a build, started by a test harness such as a `webServer`, or used for hot reload; driver sessions and daemons, and their state folders; simulators and devices; data folders and profiles; services that allow one connection at a time; and test accounts and channels. Each row says how a run claims the resource, such as a port from a range named in an env var or a session named for the run, what the run does when it's busy, how it releases it, and what doctor checks. A kind the app doesn't use gets a row that says so. Each run picks a run ID, names what it creates for it, and writes each identity it claims or creates, such as a port, a process group, a simulator's UDID or a folder's path, to an ownership file in a folder of its own, marked claimed or created. Doctor and Cleanup read that file.
- **Launch.** Exact setup and launch commands from an empty data folder to a usable state, environment variable names (never secret values), the readiness signal, the build being run, and teardown. A server or UI runs as one instance this run owns. A CLI or TUI gets a fresh isolated session for each drive. Launch claims each resource the way the inventory says, starts the app in its own process group, such as with `set -m` before starting it in the background in bash, checks that the group's ID is the PID of the process it started (`$!`) and not the shell's own group, and writes it to the ownership file. A later step that starts a screen recorder or a browser records its group the same way.
- **Doctor.** A read-only check that the instance is the one this run owns, on the expected build, port and profile, ready, and signed in when it needs to be, plus each check in the inventory's doctor column. Run it before driving and after anything surprising. Relaunch a stuck UI even when its process looks healthy.
- **Drive.** Literal commands and selectors from the repo, the starting state, waits on observable conditions, and assertions. Match labels as rendered, and prefer stable handles to coordinates. Judge each result by [What counts as a pass](#what-counts-as-a-pass).
- **Evidence.** Capture the action and the resulting state through the real user path, plus a second view of any side effect, such as a written file or row. Record the revision, feature ID and entry point. Mock only at an existing production boundary and say so. When the safe path is a dry-run mode, observe what it skips (files, network, git) instead of trusting its name. Keep captures at an ignored or external path and link `EVIDENCE.md` for PR proof.
- **Cleanup.** Read the ownership file first. Including after failed attempts, kill each whole process group it names, screen recorders and browsers included, sending SIGINT first and waiting for a recorder to finish its file, and stop each daemon it names. Then release each resource the way the inventory says. Releasing what the run created, such as a simulator, a build or derived-data folder, a driver's state folder or a temp data folder, means deleting it: after a pass once the run's captures check out as nonempty, and after a failed attempt too. List them before deleting, check that the ownership file marks each one created and that its name carries the run ID, so the run deletes only what it created, and list them again after, so the output shows each one gone. Last, list the survivors, any process still in those groups, named in the ownership file or listening on a port the run claimed, and anything marked created that still exists, and fail when any remain. Only the captures stay, and they survive every teardown, including the harness's own.

An inventory has this shape, with the app's own resources and names:

| Resource | How a run claims it | When it's busy | How it's released | What doctor checks |
| --- | --- | --- | --- | --- |
| Dev server port, also the harness's `webServer` and the hot-reload port built into the app | the first free port in the range `VERIFY_PORTS` names, picked before the build | takes the next free port | its process group is killed | it answers on 127.0.0.1 only, from the recorded group |
| Driver session and daemon | named `verify-<run id>`, its state folder in the run's folder | new each run | daemon stopped, state folder deleted | the session and daemon are the recorded ones |
| Simulator | created as `Verify <run id>` | new each run | deleted by its recorded UDID | it is booted, with the recorded UDID |
| Build or derived-data folder | the run's own path | new each run | deleted | the installed build came from it |
| Service that allows one connection per token | a lock named for the token | refuses, naming the run that holds it | lock removed once the connection closes | the lock names this run |

Put deterministic steps in tested [scripts](#scripts), and call them from the skill. Keep judgment in prose: what to drive, which states matter and what counts as proof.

`features/README.md` is the index. It holds the baseline state, driving conventions, a `What counts as a pass` section, how to report proof and skips, a link to each feature file on disk, and a short `Not mapped yet` list of features no replay has driven, each with its reason. Each feature file has an H1, a short paragraph on what the user sees, and exactly these H2s in this order:

1. `Sub-features`: short stable IDs, one observable behaviour each.
2. `How to get to it (user POV)`: every entry point a user has.
3. `Driving it with <harness>`: preconditions, then pairs of exact action and observable result, ending with what proves the end state and how that proof was seen failing.
4. `Gotchas`: focus, timing, prerequisites, destructive effects and harness limits.

[The example map](references/feature-map-example/README.md) and its two feature files show the shape. Copy the shape, not the commands.

## Scripts

Script each deterministic step that is easy to get wrong: launch and readiness, doctor, claiming ports, seeding and cleaning fixtures, credential setup, and publishing. Reuse the repo's scripts and harness where they implement the step; add the missing behaviour under the verify skill's `scripts/` folder. Keep feature actions and assertions in the driving harness.

For a web app, create includes an executable launch-and-doctor script with `launch`, `doctor` and `cleanup` commands and a runnable test. That script owns port claiming from the isolation inventory, readiness, the process group and ownership file, and Cleanup's survivor check. Implement the existing Hazards, Isolation, Launch, Doctor and Cleanup rules there. The skill's Launch, Doctor and Cleanup sections call it with an explicit run ID or ownership-file path, so each call selects its own instance. Other deterministic steps can share the script or have their own helper.

Every script:

- Runs without prompts, supports side-effect-free `--help`, and documents its inputs, prerequisites and exit codes. Exit zero only on success; distinguish a failed check or operation from invalid usage.
- Keeps secrets out of commands, logs and errors, including child-process output. Credential setup reads the repo's declared secret source, checks variable names and presence, and writes only to this run's private storage.
- Has a runnable behaviour test and an exact test command in the skill. Test its success and failure paths through its CLI, using scratch resources and stubs at external boundaries, without real secrets or API quota. For launch, cover a busy port, exhausted port range, readiness failure, stopped and stale instances, and cleanup after a partial launch. Check that cleanup removes owned descendants and created resources, preserves a different run and captures, fails on survivors, and can run twice.

Run this portability checklist for every script and record the commands and results:

- **Clean PATH.** Run the script and its test in a non-login shell with a PATH containing only the host's safety wrappers first, declared prerequisite directories, repo-local tools and system tools. Exclude unrelated global installations and shell startup files. Name each prerequisite and where it comes from; a missing tool fails with its name and setup command.
- **GNU and BSD.** Prefer the repo runtime's filesystem, temporary-directory and process APIs. Exercise any platform-sensitive utility calls with both GNU and BSD tools, especially `mktemp`, `sed`, `date`, `readlink` and `ps`. Use a common invocation or a tested capability check. Record an unavailable platform under `Not checked` rather than claiming it passed.
- **Real paths.** Resolve both paths before an entry-point comparison or ownership check. Test invoking through a symlink, including macOS `/tmp` resolving to `/private/tmp`, and from another working directory.
- **Quota fallback.** For each API-backed helper, force quota exhaustion in its test and prove a bounded fallback that preserves the operation, such as REST when GitHub's GraphQL quota is exhausted. When no safe equivalent is available, keep the local artifact and exit nonzero with the blocked operation and retry instructions. Keep credentials out of diagnostics and never silently skip publishing. For a helper with no external API, record why this check does not apply.

Complete when each applicable step has a script the skill calls, every script's test ran, and every checklist item has a recorded result or an explicit `Not checked` limitation.

## What counts as a pass

A check that has never been seen failing proves nothing. Create sees doctor and each final assertion fail once and records how. A later run sees a check fail again only when it changes that check. The index's `What counts as a pass` section states these rules in the app's own terms, with how doctor was seen failing, and every run judges its results by them, create's included:

- Doctor fails against a stopped instance and against a stale one, such as an instance still on an earlier build or started with another data folder.
- Each drive's final assertion has run once where its effect is absent, such as on the base revision, with the feature off or before the state is reached, and failed. The feature file records how, or why no run can make the effect absent.
- Zero tests, any skipped test or any retry is not a pass. A drive that has flaked once runs twice in a row with retries off, and passes both times.
- A measurement shows that something was measured, such as a non-zero sample count.
- Each feature has at least one unmocked recipe. A mocked recipe is labelled UI-only and lists its mocks.
- Open each capture before keeping it, and check that it shows the requested state.

## Create

A skill written from a reading of the repo comes out generic, so create runs the app first, writes the skill from what worked, and has a fresh agent replay it.

1. **Run.** Learn how the app runs. Read the agent instructions, README, manifests, CI, `EVIDENCE.md` and any existing harness. Pick the driver by the tiers in evidence's [surface recipes](../evidence/references/surfaces.md#who-drives-the-surface). Plan isolation with the inventory and hazards in [What a verify skill contains](#what-a-verify-skill-contains), and keep to them from the first command, so your own runs claim and release resources the way the skill will. Keep user state outside the repo. Before the first command, pick a record path outside the repo, and run every command through the recorder: `node <this skill's folder>/scripts/record.mjs <record> '<command>'`. It prints what the command printed, exits with its status, and appends the command, its exit status, its output, how long it took and the load average to the record. When the driver is the repo's own harness, such as Playwright specs, Maestro flows, an e2e test script or `cargo test`, run the harness through the recorder. That run is the recorded command, and each feature's assertions go in a spec file the harness reads, an existing one or one added under the skill's folder. Build and test the deterministic setup helpers by [Scripts](#scripts), then run those helpers through the recorder. Keep feature assertions in the harness; use a probe only for a check it cannot express. Then get one surface usable from a clean environment: a fresh shell, nothing left running from an earlier attempt, and every tool either from the repo or named as a prerequisite. Ready means usable: launch reaches a usable state from an empty data folder, including any migrations and seed data. A port that answers, or a health check that passes while init still runs, is not ready. Drive and capture the top three to five features with the driver, taken from real commands, routes, menus or docs. Then see each check fail once, as [What counts as a pass](#what-counts-as-a-pass) says: stop the instance and run doctor, run doctor again against a stale instance, run the production guard alone, with the setting that names the environment unset and again set to a name it doesn't allow, and see it refuse both times, or record why the app has no production to guard, and run each driven feature's final assertion where its effect is absent. Tighten a check that passes there until it fails there and still passes where the effect is present. When no run can make a feature's effect absent, record why. When the app cannot start, report the exact blocker and stop.
   Complete when one surface is usable from an empty data folder, each of those features was driven or failed, the record shows doctor failing against a stopped and a stale instance, the production guard refusing an unset and an unknown environment, or why the app has no production to guard, and each driven feature's final assertion failing where its effect is absent or why it can't be, and the record holds every command the run ran.
2. **Record.** Go through the record before writing anything. Mark each command that worked with the output that showed it worked, and each that failed with the error, why it failed and what fixed it. A command run to see a check fail worked only when the check failed, so mark it with that failure. A journey the seed data can't satisfy fails, and its reason goes in that feature's Gotchas, or beside the feature under `Not mapped yet` when none of its journeys passed. Never weaken a journey to make it pass. When the run used a stand-in for the real target, such as a simulator for a device or a local stack for a hosted one, add to the record every setup step the stand-in did that the target won't.
   List every resource a command claimed or created, such as a port, a session, a daemon, a simulator, a folder or an account, with how it was released. That list is the inventory's first draft.
   Complete when every command in the record is marked as worked or failed, every failure has its cause, and every resource a command claimed or created is listed.
3. **Write.** Write Hazards, Isolation, Launch, Doctor, Drive, Evidence and Cleanup from the record alone. Call the tested scripts for deterministic steps, with their exact invocations and test commands; keep the inventory and driving decisions in prose. Where the repo owns a value that can change, such as a tool's version pin, a fixture's dates or a list of test users, write a pointer to the file that owns it, or the command that prints it, in place of the value, and say in the skill that it points instead of copying, so a later edit keeps it that way. Write the index's `What counts as a pass` from it too, with how doctor was seen failing, and end each feature's proof with how it was seen failing or why it can't be. Put each failure a later run could hit beside the step it breaks, with its symptom, cause and fix. List the stand-in's extra setup steps as unverified until a run on the real target covers them. Give a feature a file only when the run drove it, and list the rest under `Not mapped yet` in the index, each with its reason. Check that each agent host the repo has instructions for, such as Claude Code for `CLAUDE.md` and Codex for `AGENTS.md`, finds the skill in the folder it reads: `.claude/skills/verify-<app>/SKILL.md` for Claude Code and `.agents/skills/verify-<app>/SKILL.md` for Codex. Where that path doesn't resolve, add the link the host reads, such as a relative symlink from `.claude/skills/verify-<app>` to `../../.agents/skills/verify-<app>`, so every host loads the skill by name, and leave user settings alone. Add one line to `EVIDENCE.md` linking the skill, or suggest `/evidence` when the repo has no `EVIDENCE.md`.
   Complete when every deterministic step calls its tested script, the script tests and portability checklist have recorded results or named limitations, every command in the skill appears in the record, every value the repo owns elsewhere is a pointer to its owner, each hazard names the step or guard that keeps it, the inventory has a row for each resource the record lists, the index matches the feature files on disk, each feature's proof says how it was seen failing or why it can't be, and each of the repo's agent hosts finds the skill.
4. **Replay.** Run the skill's Cleanup so nothing of yours is running, and delete what your own runs created the same way, checking each one against your record. Then start a fresh subagent with only the new skill and none of this conversation, or a fresh headless session when the host has no subagents. Give it the skill's path. Ask it to run the scripts' test commands, then follow Launch, Doctor, one drive for each mapped feature with its capture, and Cleanup, exactly as written and changing nothing, and to run Cleanup even after a failure. Ask it to report each result, judged by the index's `What counts as a pass`, every resource it claimed or created, what Cleanup listed before and after, and every question it had to answer for itself and every step it improvised, each with what it chose and why. Run it in the foreground and wait for its report, because a replay left in the background can stop with nobody watching. Run replays one after another, never two at once, even for two skills in one repo, because one replay's load stretches the other's timings into false gaps. The check in step 5 is the only time two runs overlap. Before and after each replay, run `uptime` through the recorder, so the record holds the load average the replay ran under. A timeout learned under load, with the load average above the core count, goes into the skill only with its idle timing beside it.
   Then sort the report. A gap is a step that failed as written, or a question or improvised step where another reasonable choice could have failed a step or let it pass without proving what it claims, such as a command that errors, a wrong value or a wait the replay saw a step needed. A precaution the replay added is a gap too when the step without it could change the user's data, cross into another run, or touch something the skill says to leave alone, such as checking for another open run before stopping one. A resource the replay touched that the inventory doesn't name is a gap too. Everything else is a nit, where any reasonable choice ends the same, such as a capture's file name, a command any agent would write the same way, two places that disagree about a check that passes either way, or any other precaution, such as a sleep or a read. Fix each nit in the skill, and run any command a fix adds through the recorder. Only a gap earns another replay: run each fix yourself through the recorder, fix the skill, then replay with a new subagent. A feature a replay can't drive gets a fix and another replay, or moves to `Not mapped yet` with its reason. When this skill caused a gap, fix this skill too. When a gap in one skill applies to another skill in the same repo, such as a single run pointer that lets two runs stop each other's process, fix both, and count it as a gap of the sibling's own, so a sibling whose last replay had no gap replays again, within its own three replays.
   Stop after the first replay with no gap, or after the third replay you start, because a replay that builds the app can take twenty minutes or more. Fix the third replay's gaps the same way and stop there: move a feature it couldn't drive to `Not mapped yet`, and name each fix no replay ran in your reply. After the last replay, confirm its captures still exist and are not empty, and that each simulator, build folder and state folder it created is gone. When the base moves after the last replay, such as main gaining a commit that changes a pinned version, run Launch, Doctor, each drive and Cleanup again on the new base. When any of them has to change, replay once more within the three replays, or name each fix no replay ran in your reply and under Not checked in the PR that ships the skill.
   Complete when the last replay drove every mapped feature, it had no gap or was the third replay with each gap fixed and named in your reply, the inventory names every resource the last replay touched, the skill's steps ran on the base it ships on, Cleanup's survivor list was empty in the last replay, no process this run or a replay started is left, nothing either created is left but captures, and the last replay's captures survived cleanup.
5. **Share.** Check that two runs can share the machine: start two fresh subagents at once, in the foreground, each with the replay's brief but driving only the quickest mapped feature. Keep this check's timings out of the skill. Both pass, or one refuses cleanly: it names the resource it found busy and stops before changing anything, and the other still passes. A collision, such as one run's doctor finding the other's instance or one run stopping the other's process, needs a fix to the inventory and the step it breaks, proved by running this check again rather than another replay. When the second check still collides, make Launch refuse while another run holds that resource, with a claim two runs can't both win, such as `mkdir` of a lock folder, and run the check once more. When that third check collides too, stop and report create as incomplete, naming the collision.
   Complete when the concurrent replays passed or one refused cleanly, the inventory names every resource either touched, Cleanup's survivor list was empty in both, and nothing they started or created is left but captures.

## Check

Edit only the verify skill's folder. Report broken app behaviour and leave product code alone.

1. Pick the target, usually the only `.agents/skills/verify-*/`. With several, ask which one. With none, run `create`. Fix missing, duplicate or dead links in the index.
   Complete when the index lists exactly the feature files on disk.
2. Read each feature from source. Hand each feature to a native subagent on the thread's model. With no subagent available, read them yourself and say so. Each feature needs a summary, its source entry points, likely drift with citations or "none", and one live recipe. Spot-check the drift citations, and scan recent source changes for user-facing features the map lacks. Name a source path before calling a feature missing.
   Complete when every feature has a source summary and a live recipe.
3. Drive every feature live, yourself and one at a time, even when the source looks clean. Follow the verify skill's launch model, and run doctor before the first drive, on each fresh session and after any failure. A feature counts as unreachable only with the route you tried and the missing prerequisite, such as auth or an OS version. Add that prerequisite to the map. Re-drive every harness fix before counting it.
   Complete when every feature has a live result or a named blocker, no process this run started is left, and earlier captures still exist.
4. Sort what you found. Fix the map where a description is wrong or missing. Fix the skill or its helper where working behaviour cannot be driven, then re-drive. Report broken app behaviour with its steps and the expected and actual result. Re-read every changed file and run `/verify` on any helper.
   Complete when every finding is fixed and re-proved, or reported.

Report one outcome, with per-feature coverage, the entry points driven, capture paths and the revision:

- `clean` when every feature has source and live coverage and nothing changed.
- `changed` with the proven corrections as one local diff, or as one PR through `/apr` when the user asked to ship.
- `blocked` with the feature, the route tried and what is missing.

Changes to this skill are measured with [its eval](evals/README.md).
